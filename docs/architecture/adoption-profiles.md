# Adoption Binding

Status: canonical.

Purpose: explain how ETHOS binds an adopter without cloning product governance
or inventing repository-type profiles.

See also: [Documentation Root](../README.md), [Command Plane](../reference/command-plane.md), [Glossary](../reference/glossary.md), [Configuration Plane](../reference/configuration.md) and the [repository-governance specification](../../openspec/specs/repository-governance/spec.md), whose "Repository profile is a strict current binding" owns the profile.

`ethos adopt` composes one ETHOS binding with native OpenSpec initialization.
It writes one declaration; the repository paradigm also admits optional
`release.toml`, `rules.toml` and `workspace.toml` beside it:

```text
.ethos/profile.toml
```

Adoption writes the minimal declaration:

```toml
profile_id = "<repository>"

[openspec]
material_paths = ["**"]
```

The strict frozen repository-profile declaration owns validation and TOML
serialization. It binds adopter identity and OpenSpec material paths. The
selected official OpenSpec package owns configuration generation, field meaning,
schema resolution and templates. Its existing `config.yaml` or `config.yml` is
preserved byte-for-byte; absent configuration is generated by the same native
serializer and schema default used by `openspec init`. ETHOS invents neither
project context nor artifact rules. No placeholder files or unrelated surfaces
are created.

```bash
ethos adopt --root <repo> --json
ethos adopt --root <repo> --apply --authorize --expect-head <git-head> --expect-plan-digest <preview-digest> --json
```

The preview reports exact file effects and native input identities. Apply
re-observes them; the optional expected-plan digest binds that reviewed input
set, including schemas and templates. Invalid native configuration, ignored-field
warnings and missing required templates prevent writes. Unavailable native supply
is UNKNOWN, not malformed user content. Existing nonempty ETHOS bindings are
never implicitly merged, overlaid, aliased or migrated.

Each file replacement is atomic. Caught failure compensates owned writes and
does not overwrite an intervening writer's content. This is not a multi-file
crash-atomic transaction or a sandbox against non-cooperating processes.
Successful binding and native readiness are not executed repository proof.
Docs, Skills and provider CI remain optional, separately owned capabilities.

The declaration may point at existing repository-owned `rules/`, `openspec/`,
`docs/`, and `.agents/skills/` roots. Their
presence is capability state, not a bootstrap prerequisite. Domain gates,
provider state, and tool-native configuration remain adopter facts; adoption
does not generate or normalize them. The repository paradigm fixes the
branch-role names.

The common floor that every adopter shares is the union of its owners' obligations:
repository-governance for the binding, OpenSpec, commits, release and documentation
carriers, and the Product Design Contract for the quality floor, feedback and recovery.
No Skill or generated entrypoint adds to it.

## Formation and Starter Evolution

`ethos adopt --create --root <absent-path>` previews forming a new repository at
an absent destination, and apply runs only an authorized plan bound by
`--expect-plan-digest`. Without `--create`, `adopt` keeps binding an existing
repository at its exact HEAD and writes no scaffold. Formation stages its
candidate in a disposable directory named for the project, binds the requested
path and its parent's device and inode into the plan digest, and on apply
refuses a changed parent, an existing target or a link before it creates the
target exclusively. `ethos mcp --create-target --root <absent-path>` binds one
absent target for formation only; every call refuses retargeting, and creation
still requires an authorized `adopt` plan digest.

Starter evolution merges the recorded starter output, the authored HEAD and the
installed generator's new output with native `git merge-tree`.
`ethos adopt --evolve-starter` previews that patch from the formation
Attestation and refuses `--apply`: a clean result is only a reviewable candidate
that lands through exact-path prewrite in an owned Work Lane, and a conflict
leaves authored bytes untouched. Package-owned starters keep their upgrade
provenance in the formation Attestation, so a template engine such as Copier is
not their update owner; a project formed by Copier may keep it as an optional
adapter without intent or effect authority.

`ethos adopt --select-runtime` selects the exact package runtime without
replacing a repository's incumbent hooks; runtime provenance never substitutes
for their enforcement or for full proof.

An adopted repository uses the same result and continuation semantics as the
product. The profile selects repository-owned facts and gates; it does not
create a second command plane or copy adopter semantics into the ETHOS product
runtime.

Product release policy is likewise profile-bounded. Merely having a
`pyproject.toml` does not make an adopter an ETHOS Python workspace. A
runtime-files adopter may keep its release name, distribution kind, Python
floor, and `VERSION` path under one repository-owned `[tool.<name>]` table;
ETHOS reads that declared identity without requiring a synthetic `[project]`
table or applying product-only release surfaces during generic audits.
