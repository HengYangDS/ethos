# Adoption Binding

Status: canonical.

Purpose: explain how ETHOS binds an adopter without cloning product governance
or inventing repository-type profiles.

See also: [Documentation Root](../README.md), [Command Plane](../reference/command-plane.md), [Glossary](../reference/glossary.md), [Repository Profile Contract](../governance/repository-profile-contract.md), and [Config Boundary Model](../governance/config-boundary-model.md).

`ethos adopt` composes one ETHOS binding with native OpenSpec initialization.
The sole ETHOS-owned declaration is:

```text
.ethos/profile.toml
```

The strict frozen repository-profile declaration owns validation and TOML
serialization. It binds adopter identity and OpenSpec material paths. The
selected official OpenSpec package owns configuration generation, field meaning,
schema resolution and templates. Its existing `config.yaml` or `config.yml` is
preserved byte-for-byte; absent configuration is generated by the same native
serializer and schema default used by `openspec init`. ETHOS invents neither
project context nor artifact rules. No placeholder files or unrelated surfaces
are created.

```bash
ethos adopt --root <repo> --json
ethos adopt --root <repo> --apply --authorize --expect-head <git-head> --expect-plan-digest <preview-digest> --json
```

The preview reports exact file effects and native input identities. Apply
re-observes them; the optional expected-plan digest binds that reviewed input
set, including schemas and templates. Invalid native configuration, ignored-field
warnings and missing required templates prevent writes. Unavailable native supply
is UNKNOWN, not malformed user content. Existing nonempty ETHOS bindings are
never implicitly merged, overlaid, aliased or migrated.

Each file replacement is atomic. Caught failure compensates owned writes and
does not overwrite an intervening writer's content. This is not a multi-file
crash-atomic transaction or a sandbox against non-cooperating processes.
Successful binding and native readiness are not executed repository proof.
Docs, Skills and provider CI remain optional, separately owned capabilities.

The declaration may point at existing repository-owned `rules/`, `openspec/`,
`docs/`, and `.agents/skills/` roots. Their
presence is capability state, not a bootstrap prerequisite. Branch-role names,
domain gates, provider state, and tool-native configuration remain adopter
facts; adoption does not generate or normalize them.

An adopted repository uses the same result and continuation semantics as the
product. The profile selects repository-owned facts and gates; it does not
create a second command plane or copy adopter semantics into the ETHOS product
runtime.

Product release policy is likewise profile-bounded. Merely having a
`pyproject.toml` does not make an adopter an ETHOS Python workspace. A
runtime-files adopter may keep its release name, distribution kind, Python
floor, and `VERSION` path under one repository-owned `[tool.<name>]` table;
ETHOS reads that declared identity without requiring a synthetic `[project]`
table or applying product-only release surfaces during generic audits.
