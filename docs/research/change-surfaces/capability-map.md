# Capability Map: GitHub and GitLab Side by Side

Research date 2026-11-18. Review by 2027-05-18, or when the licence tier of the GitLab instance is
established.

Question: for each purpose that a repository's forge state serves, which capability does each
forge offer, can one model declare both, and where can the two not be made the same?

The capabilities, their plans and tiers, and their sources are in
[Forge capabilities](forge-capabilities.md); row numbers below point there (GH for GitHub's table,
GL for GitLab's). The two right-hand columns are this study's reading. "One model" asks whether
one declaration of a role could be projected to both forges, as ETHOS's CUE model already
projects one pipeline definition to two files. GitHub is read as a public repository of a user
account with the Free plan's features; GitLab's tier is given with each capability because the
instance's tier is not known.

## What the map says

Reading.

- **A common floor exists at GitLab's Free tier.** One model can hold, for both forges: which
  branches are protected and who writes them; that force pushes and deletions are refused; the
  tag pattern and who creates tags; that hosted verification passes before a merge; that threads
  are resolved; the labels and milestones; the entry documents; description and topics; the
  switches for wiki, Pages and registries; auto-merge and branch cleanup; and the pipeline, which
  is already one model.
- **Four wanted controls have no forge enforcement on GitLab below Premium:** signed commits, a
  required approval, code owners, and limits on a push's content. Where the instance has no such
  licence, either ETHOS's own gates carry them on both forges, or the model states that a control
  is enforced by the forge on GitHub and by ETHOS on GitLab.
- **Three purposes cannot share a model at all:** attestation of builds and releases, the
  dependency and secret services, and boards. Each forge has its own object, and for the first
  two ETHOS already has a forge-neutral carrier of its own.
- **Some differences are of owner, not of feature.** Issue types and Projects belong to a GitHub
  account, team reviewers and custom properties to an organization, epics and compliance
  frameworks to a GitLab group. A repository's own declaration cannot reach them.
- **The carrier differs even where the fact is the same.** A schedule is a file on GitHub and a
  setting on GitLab; required checks are forge state on GitHub and pipeline content on GitLab. A
  model has to name the fact once and let each projection choose a file or an API call.

## Not verified

- Every "none found" and "not read" above is the limit of the pages read, not a finding about the
  forge.
- Whether the GitLab instance holds a Premium or Ultimate licence, which would change the rows on
  signatures, approvals, code owners, push content, queues and guarded release steps.
- Whether one identity can be the sole writer of a protected line on both forges in the way that
  `ethos publish` needs; the bypass modes of a GitHub ruleset were not read.
