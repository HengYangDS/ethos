# Forge Capabilities: What One Repository Has on GitHub and on GitLab

Research date 2026-11-18. Review by 2027-05-18, or when the licence tier of the GitLab instance is
established, or when either forge ships a declarative file for repository settings.

Question: which capabilities does one repository have on GitHub and on GitLab, which of them does
ETHOS's own repository use today, which mature tools declare and enforce a repository's forge
state as code, and what do public standards ask of a repository's forge state?

Every source below is the forge's, the tool's or the standard's own page or file, read on
2026-11-18. GitHub's pages are those of the Free, Pro and Team documentation unless the Enterprise
Cloud page is named. GitLab's pages are the documentation's source files at the branch of the
instance's version (`19-5-stable-ee`); "tier" quotes each page's or section's own `Tier:` line.
ETHOS's state is the lead's read of both forges' APIs of 2026-11-18 and the tree at `e4d9d04d3`,
read at 14:52; this study asked no forge anything. The API answers are kept with the study's
working files and are not tracked here; a file name in a cell, such as `repo.json`, names the
answer that the claim rests on. The findings report
what the sources and the data say. The sections marked as reading, and the three closing
sections, are this study's reading. It decides nothing.

The numbered rows of the two capability tables were read again on 2026-11-19 by a second reader.
GitHub's 53 rows were held against `docs.github.com`, and the plan box of 18 of them against
the documentation's source; three plan cells changed (rows 5, 37 and 53). GitLab's 44 rows were
held against the current site, and the five rows where that site differed against the branch
named above; four cells changed (rows 23, 27, 31 and 43). The column on ETHOS's own use was not
part of that reading.

[Capability map](capability-map.md) puts the two forges side by side by purpose. For hosted CI
practice (pinning, tokens, runners, caches, queues) see the earlier study
`docs/research/foundations/hosted-ci.md`, whose items are cited here by number and not repeated.

Reading. Three of the rows do not fit ETHOS's repositories as they are: safe-settings and Allstar
work on an organization and ETHOS's GitHub owner is a user account; the settings app widens who
is an administrator. gitlabform is for GitLab alone and asks for an administrator's token.
OpenTofu with the two providers is the one mature engine that reaches both forges and a
user-owned repository, and its `plan` is a drift report. It costs a state file, which is a second
record of forge state, a third configuration language beside TOML and CUE, and two providers that

two pipeline files. This reading would keep the declaration in ETHOS's paradigm, as roles, and
treat a tool as the executor beneath it; a design decides whether that executor is OpenTofu or
ETHOS's own audit and repair over each forge's API.

## Gaps between what the forges offer and what ETHOS uses

Reading, in this study's order of weight.

1. **Forge state is declared nowhere, and the two repositories have already drifted apart.** The
   paradigm holds no row for a forge setting. Eleven facts differ between the two repositories
   today, among them the merge method, the enforcement of signatures and the protection of release
   tags. ETHOS's own security statement rests on a forge setting that nothing in the tree checks.
   The lead's check of 2026-11-18 adds a case: the ruleset requires twelve status checks by
   name (`repository proof`, `package artifacts`, `ubuntu-latest / Python 3.12` and others), and
   the pipeline's jobs were renamed since the ruleset was written on 2026-10-26, so eleven of the
   twelve are reported by no job. A change by anyone without the bypass could not be merged, and
   nothing reports the mismatch.
2. **The release line is the least guarded part on GitHub.** No rule covers `v*`, the five
   releases are not immutable, and the job that holds `contents: write`, `id-token: write` and
   `attestations: write` runs in no protected environment. Tag rulesets and an environment's
   reviewers are free for a public repository, and the pages read state no plan for immutable
   releases; hosted CI items 5 and 7 already name two of the three.
3. **Review is declared and has no record.** The ruleset asks for an approval of the last push,
   no pull request exists, and the owner bypasses always. Scorecard, the Baseline and SLSA all
   read the forge's own record of review; ETHOS accepts a change locally and publishes it, so the
   forge shows nothing of that proof.
4. **Free security features are off or do not gate.** Push protection is disabled; there is no
   update tool and no dependency review; CodeQL reports while no rule blocks; SHA pinning is
   practised and not required; `allowed_actions` is "all". At least one Dependabot alert and one
   code scanning alert are open, since 2026-11-05 and 2026-11-09.
5. **Intake and planning surfaces are as the forge created them.** The 10 default labels, no
   milestone, no issue type, no form, no chooser and no discussions on GitHub; no label, no
   milestone and one default board on GitLab; no code of conduct.

## Patterns that at least three sources share

- A protected line means the same four things in every source that defines one: no force push, no
  deletion, checks that pass, and a second person. Scorecard's tiers, the Baseline's AC-03 and
  QA-03, SLSA's source levels, GitHub's rulesets and GitLab's protected branches all say so.
- Forge state splits into files in the tree and settings behind an API, and no forge ships a file
  for the settings. Every tool read exists to add that file: `settings.yml`, `policy.yml`, HCL,
  gitlabform's YAML, `.allstar`.
- The declaration lives in a repository and changes by review: safe-settings previews a pull
  request, the settings app syncs the default branch, `repo-policy` and OpenTofu plan before they
  apply.
- Drift is found by reading live state and comparing, either on an event (safe-settings), on a
  schedule (Allstar, safe-settings' `CRON`, `repo-policy`'s daily audit of itself) or on demand
  (`plan`, `audit`).
- The stricter the control, the higher the plan: required workflows and merge queues for private
  repositories on GitHub; push rules, required approvals, code owners, merge trains, protected
  environments and policies on GitLab.
- Tags and releases are named apart from branches: a tag ruleset and immutable releases on
  GitHub, protected tags on GitLab, a MUST in SLSA's source track, Signed-Releases in Scorecard,
  BR-06 in the Baseline.

## Where the sources disagree

- **Whether a state file is needed.** Terraform and OpenTofu keep one; `repo-policy` says "no
  state file, no backend"; safe-settings reads live state at each run, and gitlabform's pages
  mention no state.
- **Who may write the declaration.** The settings app lets anyone who can push become, in effect,
  an administrator; safe-settings keeps the files in one `admin` repository behind code owners.
- **Report or repair.** Allstar's default action is `log` and its usual one an issue;
  safe-settings reverts a manual change at once; `repo-policy` separates `audit` from `apply`.
- **Where acceptance happens.** Every standard read places it on the forge: a pull request, an
  approval, a status check. ETHOS places it in a local proof and publishes the result, so a
  control such as AC-03.01 is either met with a standing bypass or not met at all.
- **What a signed release is.** Scorecard looks for signature files among the assets; GitHub
  keeps attestations in its own store; the Baseline accepts "a signed manifest"; GitLab's keyless
  signing is offered on GitLab.com alone, and on Self-Managed only with a self-hosted Sigstore.
- **What is free.** GitHub's pages give a public repository on the Free plan nearly every
  security feature. GitLab's pages state a tier for each feature, and none of those read ties it
  to visibility: a project on the Free tier has neither push rules nor required approvals.
- **The unit that is governed.** safe-settings, Allstar, custom properties and compliance
  frameworks govern an organization or a group; `repo-policy` and the settings app govern one
  repository; ETHOS's GitHub repository belongs to a user account.
