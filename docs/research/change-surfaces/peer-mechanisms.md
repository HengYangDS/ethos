# Peer Mechanisms: How Repositories Like ETHOS Do the Work

Research date 2026-11-18. Review by 2027-05-18, or when a repository of the first two groups
below publishes a release that changes how it admits, verifies or records a change.

Question: how do public repositories that do what ETHOS does, or a part of it, bind a change to
its intent, admit a write, bound an agent, verify, record evidence, review, detect drift, handle
waivers, give agents context, release, recover and take on an existing repository; and what does
ETHOS have today for each of those problems?

The earlier study of the same day ([peers](peers.md)) read these repositories' forge files. This
one reads their product: the README, the documentation that describes each mechanism and, for
two mechanisms, the source that implements it. Each repository was read on 2026-11-18 at the
head of its default branch, through the forge's read-only API or its documentation site; nothing
was cloned, installed or run. The sections up to "Not reached" report what the sources say, with
ETHOS's side read from ETHOS's own documents and eight of its accepted requirements. The column
"Fit" is this study's reading: `take`, `adapt`, `ETHOS better` or `does not fit`. The ranked
reading is in [worth taking](worth-taking.md).

## Patterns that at least three sources share

- **The intent is accepted before the code that claims it.** OpenSpec's own repository (a
  proposal, then its implementation), intent-driven-template (a state change "must cross `main`"),
  elephant-goldfish-model (a design stage and an implementation stage), qualitylayer (one Plan
  approved "before any code is written"), Spec Kit (review gates after the specification and
  after the plan), cc-sdd (phase gates), ProductSpec ("Merge the Product Spec before major
  implementation begins") and BMAD (`plan_checkpoint`).
- **The one who wrote it does not approve it.** Reviewers with a fresh context
  (elephant-goldfish-model, BMAD, qualitylayer, cc-sdd), on another model
  (intent-driven-template, qualitylayer's second opinion), a refusal of the implementer's own
  review (ControlCoding), an allowed approver on the current head (CoaseEdge), a mark only the
  reviewer may set (Spec Kit), a split of maker and checker (loop-engineering), and a reviewer
  that can read and not write (agent-orchestrator).
- **A change declares its boundary, and the diff is compared with it.** Paths, categories and
  size in CoaseEdge; ownership, exclusions and allowed dependencies in cc-sdd; the files of an
  assessment in Spec Kit's bug workflow; `in`, `out` and `cut` in ProductSpec; a declared track
  against the diff's size in elephant-goldfish-model; a file count and a denylist in
  loop-engineering. OpenSpec records `affected_areas` and enforces nothing with them.
- **Risk is declared by path and raises what is required.** Risk zones (CoaseEdge), path rules
  for the description (maintainer-contracts), surfaces with an overseeing role (se-codeowners),
  denylisted paths and human gates (loop-engineering), a risk scored at planning (BMAD), a
  security review when a change "crosses a trust boundary" (qualitylayer). None of them infers
  risk from the code.
- **Each acceptance item is tied to its own evidence.** Numbered points shown with their output
  (qualitylayer), identified criteria with a status for each (ProductSpec), scenarios that run
  (intent-driven-template), properties linked to a requirement and a task (Kiro), a criterion
  with its baseline, and prohibitions proven to fail first (gsd-core), and coverage checks of
  requirements against tasks and design (Spec Kit, cc-sdd, OpenSpec's verify).
- **A repair loop has a bound, and most hand the exit to a person.** Five iterations (BMAD),
  two rounds and then one question (qualitylayer), three attempts and then a human gate
  (loop-engineering), hard budgets with a typed stop (agents-best-practices). cc-sdd answers
  repeated rejection with a debugging pass.
- **A deterministic engine decides and a model only explains.** CoaseEdge ("does not use an LLM
  to make hard decisions"), gsd-core (projection modules in place of workflow prose), Evagix,
  loop-engineering's gate, the harness of agents-best-practices, architekton's adapter. Where a
  model reviews (elephant-goldfish-model, BMAD, qualitylayer), a person makes the last decision.
- **A baseline, so that only what is new counts.** The architecture baseline and the task
  failure baseline (CoaseEdge), a pinned size for each instruction file (gsd-core), a baseline
  snapshot with a diff command (Evagix), findings marked "Previously seen" (qualitylayer).
- **"Could not look" is a state of its own.** `not checked` (qualitylayer), `unknown` (Evagix,
  branchrift), `unsupported` and `stale` beside `unknown` (architekton), `UNCHECKABLE` and the
  replay statuses (gsd-core), `cleanCheckoutStatus: "not-run"` (CoaseEdge).
- **The tool says what its guard does not prove.** CoaseEdge, gsd-core, architekton,
  ControlCoding, Kiro's correctness page, branchrift, maintainer-contracts and agent-orchestrator
  each state a limit in the place where they describe the guard.
- **A waiver is bound to what it covers and stays visible.** The exact diff, an expiry and a
  live approval (CoaseEdge), the function, the analyzer's configuration and the metric
  (qualitylayer), a commit trailer with the change's own lifetime (gsd-core), a justification
  with the rejected alternative (Spec Kit), never counted as evidence (Evagix).
- **Context for agents is small, pointed and thin over the tool.** A removal test for each line
  (BMAD), a byte budget for each file (gsd-core), skills that only call the locked engine
  (CoaseEdge), inclusion by path or by request (Kiro), required context kept apart from advice
  (OpenSpec), an opt-in managed block (Spec Kit).
- **Adoption starts by reading.** Reporting mode first (Evagix, loop-engineering), inspection
  before any write (architekton), audit before plan before apply and only over declared scope
  (repo-policy), opt-in contracts (CoaseEdge), six levels (ProductSpec).
- **What is found outside the change is an output, not a repair and not a backlog.** Deferred
  findings (BMAD), deferred intents (Spec Kit), failures that predate the task (CoaseEdge), a
  follow-up "with its owner" (qualitylayer).

## Where the sources disagree

- **Who judges a change.** CoaseEdge runs the engine that the candidate commit pins, in an
  isolated clone; maintainer-contracts reads the policy from the trusted base and never from
  the change. ETHOS stands with the second.
- **A boundary predicted in paths, or none.** CoaseEdge, cc-sdd and loop-engineering have a
  person declare paths before the work; OpenSpec records areas and does not enforce them; ETHOS
  rejects predicted paths for admission and for concurrency.
- **A finding blocks, or informs.** CoaseEdge's scope and budget findings are "non-waivable"
  errors and Spec Kit makes its constitution check a gate of the plan. qualitylayer's
  code-health findings "never stop the work", OpenSpec's verify "does **not** block archiving",
  and gsd-core's replay "never changes `valid` or the exit code".
- **A score, or a verdict.** Evagix, CoaseEdge's drift score and loop-engineering's readiness
  score weigh findings into a number, and the first two set a pass mark on it; qualitylayer
  ("A failure is never marked passed") and ETHOS keep each failure a failure.
- **Progress kept in a file, or derived each time.** gsd-core and loop-engineering keep a
  `STATE.md`, Conductor a `plan.md` with commit identifiers, BMAD a status in each plan; both
  gsd-core (the rebuild record) and loop-engineering ("State Rot") list the decay of that file
  among their own failures. agent-orchestrator ("Display status is never stored"), Evagix and
  ETHOS derive it.
- **A model in the review, or out of every decision.** elephant-goldfish-model, BMAD and
  qualitylayer make model review the first line; CoaseEdge allows a model to explain a report
  and nothing more.
- **Who writes the specification.** In cc-sdd "Agents write the spec, humans review the
  contract"; in CoaseEdge the boundary is "human-declared" and widening it "is a human
  authorization change".
- **Skills for the machine or for the repository.** OpenSpec 2.1 recommends a global install
  and agents-best-practices checks its main branch at each task and updates itself; CoaseEdge's
  skills only call the locked CLI, and ETHOS keeps skills matched to the selected product.
- **One piece of work at a time, or many.** ControlCoding enforces one active feature;
  agent-orchestrator, BMAD's orchestrator and cc-sdd's batch run many in parallel.
