# Control-character Path Admission Evidence — 2026-07-09

## Claim

ETHOS hook and prewrite admission reject target path tokens containing ASCII
control characters before those tokens can be resolved, joined to a repository
root, or rendered as repository-relative claims.

## Boundary

This evidence supports admission-path token validation only. It does not add a
new command plane, host escaping policy, Unicode normalization policy, or
provider ontology.

## Mechanism

- `prewrite_guard` checks the supplied path token before root joining or
  resolution.
- `hook_admission_report` preserves malformed tokens so command JSON reveals the
  exact hidden state.
- The blocked decision uses `prewrite_path_invalid_control_character`; the path
  entry uses `path_invalid_control_character`.

## Verification

Focused command output showed the pre-tool hook blocks a newline-bearing
path token with `prewrite_path_invalid_control_character`. The lane also adds a CLI contract test under the focused hook test package so
`ethos hook admit` preserves the malformed token before root joining without
growing the already-large lane contract test module. The generic shadow-parity
evidence is refreshed after this lane changes parity-relevant admission,
OpenSpec, and claim surfaces. Final focused tests, OpenSpec lifecycle, parity
gaps, report, and head-bound proof are rerun after this evidence and carrier are
committed.

## Design Judgment

This follows `几动于微`: a newline in a target path token is a small but
load-bearing signal that evidence could become ambiguous. The repair reveals the
hidden token, calibrates the target-path boundary, and keeps the existing
prewrite/hook loop as the center.
