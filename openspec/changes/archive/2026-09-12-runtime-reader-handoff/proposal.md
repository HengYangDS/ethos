## Why

An archived proof gained an execution-source binding that the installed reader
cannot validate. Repeating tests or retaining old readers cannot solve that
self-hosting boundary. The user authorizes exact local maintainer recovery and
removal of unnecessary handoff machinery, while preserving admission, proven
results and pending work. Investigation also reproduced repository-only proof
validation and trusted-predecessor control-policy gaps.

## What Changes

- Validate proof plans identically with and without an active Commitment.
- Classify execution adapters as control paths and select control verification
  from the trusted accepted policy; a candidate cannot downgrade that floor.
- Reuse native runtime installation, Git effects and existing bounded recovery.
  Do not add a prepared-evaluator API, generic hook dispatcher or compatibility
  reader. Preserve every pending input before replacing or retiring resources.
- Apply the authorized independent product/test ELOC ceilings of 50,000 in the
  existing native declaration, without changing counting, exclusions or coverage.
- Retain foundations research and actionable tool observations in their existing
  research/plan owners, with conclusions separated from implementation evidence.

The staged commit exposed a native secret-rule false positive: provider context
and a Git OID were mistaken for a credential. Refine the single native
`.gitleaks.toml` rule and exercise real scanning in
`tests/unit/adapters/repo/hook/test_execution.py`; keep positive credential and
legacy key-assignment detection. No path/hash suppression or scanner bypass.

## Non-Goals

No public handoff subsystem, new lane, alternate roadmap, adopter source write,
model change, proof rewrite, relaxed coverage or permanent hook bypass. Runtime
re-entry and lane retirement receipts remain operational evidence, not extra
source tasks that require editing an already-proven snapshot.
