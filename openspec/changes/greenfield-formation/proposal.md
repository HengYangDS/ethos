## Why

ETHOS can bind an existing repository, but it cannot form a usable new one. A
fresh adopter currently gets two configuration files and then encounters missing
Git coordination and installed-runtime admission. An Agent must reconstruct the
remaining setup from ETHOS source or prior conversation.

## What Changes

- Add an explicit, reviewable greenfield formation operation. It creates a
  working repository from an absent destination without weakening the existing
  minimal `adopt` path for brownfield repositories.
- Compose a small package-owned foundation with a selected domain starter,
  official OpenSpec initialization, Git identity and coordination, and
  version-matched Agent discovery. Do not impose one language or source layout.
- Bind generated inputs and outputs, preserve authored customization, surface
  collisions and uncertain effects, and make template evolution an explicit
  proposal rather than an overwrite.
- Verify the journey from a clean installed product through first governed
  change, Agent handoff, upgrade conflict, and exit on real target repositories.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `command-plane`: expose formation through the same typed application result
  and fresh admission as other public operations.
- `repository-governance`: distinguish greenfield formation from conservative
  brownfield adoption and preserve ownership across generation and evolution.

## Impact

The installed CLI/SDK/MCP projections, repository adoption and Git effect owners,
package resources, conformance tests, and first-hour documentation. No second
intent store, template registry, lifecycle, Agent-specific authority, or
mandatory Python toolchain is introduced.
