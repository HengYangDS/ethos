# Design

## Context

See [proposal.md](proposal.md). `src/ethos/adapters/repo/hook/binding.toml` declares one launcher template for the four hooks. `binding.py` validates it, renders one launcher per hook and digests them into the hook generation that `core.hooksPath` names. Status compares the installed launchers with the declaration of the selected runtime, read from that runtime's own package (`observation.py`), so a repository whose launchers and runtime come from the same release is current.

The probe used Git 2.56.0 in a scratch repository:

| Operation                              | Hook invocations               | Prepared |
| -------------------------------------- | ------------------------------ | -------- |
| `git update-ref refs/heads/probe HEAD` | preparing, prepared, committed | 1        |
| `git commit --allow-empty`             | 7 in total                     | 2        |

A launcher that exits 0 before reading stdin in the other states passed a 3,000-line `update-ref --stdin` batch, with every ref written. A launcher that exits 9 in committed still let `update-ref` succeed. One no-op protocol start took 0.13 s at load 5.5. Before this Change, the eight heaviest tests took 218 s user and 173 s system CPU, run one at a time.

## Goals / Non-Goals

**Goals:**

- The runtime starts only for the states ETHOS governs.
- Launchers generated by earlier runtimes keep working, and status does not block them until their repository reinstalls hooks.
- One rule: only prepared is governed.

**Non-Goals:**

- Changing prepared admission or the policies it applies.
- Changing `ethos hook ref-transaction`, whose `--phase` option evaluates one update interactively.
- Making the prepared path itself cheaper.

## Decisions

### 1. The declaration names the governed states

`binding.toml` gains `phases = { reference-transaction = ["prepared"] }`, and its template gains one `@GUARD@` line. `binding.py` renders that line as `case "$1" in prepared) ;; *) exit 0 ;; esac` for a hook that names states, and removes it for the others. The guard runs before the launcher reads `CURRENT`, so a skipped state touches neither the runtime selection nor stdin. `case` is plain POSIX `sh`, as the launcher's existing selector checks already are, so Git for Windows' `sh` runs the same bytes.

### 2. Earlier declarations stay valid

A declaration without `phases` and without `@GUARD@` is still accepted and rendered as before. Status reads the declaration of the selected runtime, so a repository still bound to an earlier runtime keeps current launchers. `ethos hook install` writes the new generation and the new launchers together when a repository rebinds.

### 3. The protocol keeps one rule

`protocol.py` answers every state other than prepared with `phase_not_governed`, before it reads stdin. The separate committed and aborted branch goes away. A test first shows that the preparing, committed and aborted states leave the ETHOS state directory byte for byte unchanged, with no journal and no attestation, so removing the branch removes no effect. ETHOS's own ref effects claim their prepared, committed and aborted intents in the executor (`git_effects.py`), not in the hook.

### 4. Acceptance counts launches

A launcher test runs the rendered reference-transaction launcher through Git with a stub runtime that records each start. Before the guard, a commit started it for the preparing, committed and aborted states as well. With the guard, it starts only for prepared states, and once for `update-ref`. The eight heaviest tests, run one at a time under `/usr/bin/time`, used 218 s user and 173 s system CPU before and 192 s user and 135 s system CPU after, a 16 percent cut (391.7 s to 327.3 s). Their wall time fell from 381 s to 320 s at a lower load, so the CPU time is the comparison.

## Risks / Trade-offs

- [A future ETHOS feature needs a terminal state] → It declares that state in `phases`, and the launcher passes it through.
- [Malformed input in a terminal state is no longer reported] → Git ignores those exit statuses, so nothing was enforced. Prepared input is still parsed strictly.
- [The launch-count test needs a POSIX `sh` stub] → It is skipped on Windows. The rendering test runs on both platforms, and the guard uses only the `case` form that the launcher already uses there.
